## CiTO

- [Pull request](https://github.com/SPAROntologies/cito/pull/7): Sperimentazione con [codespell](https://github.com/codespell-project/codespell), uno spell checker per codice sorgente
    - piano: testarlo (come strumento di reporting, come strumento di fixing e come workflow in GitHub Action) su un'ontologia piccola e separata dalle nostre (miglior candidata: [HeRO](https://w3id.org/sirius/ontology/hero/))
    - le ontologie rappresentano un caso d'uso interessante per `codespell` perché contengono termini tecnici e/o di dominio che possono sembrare typo ma non lo sono
    - potrebbe essere quindi necessario fare tuning della configurazione tramite `.codespellrc` estendendo i valori da ignorare in `ignore-words-list`
    - prossima evaluation:
        - fare run in modalità report e verificare che i typo individuati esistano veramente
        - se ci sono falsi positivi, li aggiungo in `ignore-words-list`
        - se i falsi positivi sono pochi e gestibili, potrebbe valere la pena di aggiungere un meccanismo di CI

```
# Codespell configuration is within .codespellrc
---
name: Codespell

on:
  push:
    branches: [master]
  pull_request:
    branches: [master]

permissions:
  contents: read

jobs:
  codespell:
    name: Check for spelling errors
    runs-on: ubuntu-latest

    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Codespell
        uses: codespell-project/actions-codespell@v2
```

## VAULT

Ho iniziato a sviluppare **VAULT** (nome temporaneo, appena ho due neuroni attivi in più mi impegno per un nome un po' più carino), uno strumento leggero per monitorare l'uptake di ontologie. 

### Repo

https://github.com/sbrzt/vault/

### Demo

https://sbrzt.github.io/vault/

### Descrizione

- Uno script Python che genera un report HTML contenente uno snapshot dell'utilizzo/riferimento a determinate ontologie (definite in `config.yaml`), con un workflow GitHub Actions che lo tiene aggiornato mensilmente
- Obiettivo: individuare una serie di segnali (intesi come evidenze osservabili, informative e misurabili) in maniera automatizzata come proxy di adozione delle ontologie a cui siamo interessati
    - un paper che menziona l'URI di un'ontologia è un segnale che gli autori sono consapevoli dell'esistenza di quella ontologia e che la citano
    - una repo contenente l'URI in un file `.ttl` o `.py` è un segnale che gli sviluppatori la stanno utilizzando in dataset e in script di generazione, processamento o materializzazione di dati
    - un'ontologia che importa, specializza, o estende un'altra ontologia, o che contiene almeno un termine che è definito in un'altra ontologia, è un segnale che quest'ultima riceve abbastanza attenzione da essere riutilizzata da altri
    - l'idea è quindi combinare segnali multipli per costruire una rappresentazione approssimata ma sufficientemente precisa dell'uptake delle nostre ontologie
- VAULT conta i riferimenti alle ontologie sulla base di una serie di euristiche applicate su 3 fonti:
    - **LOV** (API + SPARQL endpoint): segnale mediamente debole, ma secondo me necessario
        - raccoglie i metadati dei vocabolari presenti su LOV e conta le volte in cui vengono utilizzate certe proprietà aventi come valori i namespace delle ontologie monitorate 
        - raccoglie i contenuti delle ontologie e conta le volte in cui vengono utilizzate certe proprietà aventi come valori i namespace delle ontologie monitorate
        - segnale abbastanza deludente perché si basa sull'utilizzo di proprietà che non tutti usano
    - **GitHub** (API): segnale molto forte
        - inizialmente ho provato con Software Heritage, ma ho riscontrato problemi con le possibilità offerte dall'API: in particolare, da quanto ho capito, è impossibile accedere in maniera diretta ai contenuti delle repo archiviate
        - mi sono quindi spostato su GitHub, il quale invece mi permette di accedere in maniera semplice e veloce ai contenuti delle repo pubbliche
        - voglio accedere ai contenuti dei file nelle repo perché l'euristica in questione si basa sulla presenza delle stringhe rappresentanti i namespace delle ontologie monitorate all'interno di file `.ttl`, `.rdf`, `.owl`, `.jsonld`, `.sparql`, `.rq`, `.md`, `.py`, `.js`, `.java`
        - necessita di un fine-grained token generato su GitHub e salvato come variabile in `.env` oppure come segreto su GitHub Actions
        - evito il rate limit di 10 richeste al minuto utilizzando un time.sleep di 6 secondi 
        - per ora ho settato il cap a 100 file
        - segnale forte e interessante
    - **OpenAlex** (API): segnale forte
        - prende il numero di articoli in cui vengono menzionate delle keyword configurate in `config.yaml` (al momento sono solo i namespace delle ontologie) e lo visualizza a schermo assieme ad un bar chart che visualizza il numero di articoli per anno e a una lista dei top articoli più recenti con una serie di metadati (titolo, autori, anno di pubblicazione, venue, DOI)
        - da quello che mi risulta, le dimensioni di ricerca sono `title`, `abstract` e `fulltext`. Utilizzo il parametro `search.exact` per effettuare una ricerca senza stemming
        - l'idea è buona, l'euristica sembra essere abbastanza efficace, ma nel dietro le quinte di OpenAlex succedono cose strane, come stemming e tokenization anche qualora non sono desiderabili (es se come keyword cerco "Citation Typing Ontology", questo viene tokenizzato e manipolato per cercare anche solo "citation")
        - devo sperimentare con il phrase matching. Non credo mi servano le funzionalità più avanzate tipo proximity search, semantic search e compagnia bella
- 3 helper script per raccogliere, caricare e renderizzare i dati 
    - il caricamento della configurazione passa anche attraverso una validazione per essere sicuri che `config.yaml` non sia rotto
    - la raccolta dei dati avviene tramite richieste HTTP GET e funzioni di fetching diverse:
        - prima di fare qualsiasi altra cosa, prende info utili da LOV riguardanti le ontologie monitorate, poi scarica tutti i vocabolari da LOV e fa vari check a livello di metadati e contenuti di ogni vocabolario
        - nei metadati del singolo vocabolario considero:
            - `voaf:metadataVoc`
            - `voaf:specializes`
            - `voaf:extends`
            - `voaf:reliesOn`
            - `owl:imports`
        - nei contenuti del singol ovocabolario considero:
            - `owl:imports`
            - `rdfs:isDefinedBy`
        - per ogni vocabolario produco risultati in JSON (URI del vocabolario + data di ultima modifica del vocabolario) e li metto in cache così da velocizzare il processo successivamente con un light check sulla data
        - parallelizzo la raccolta dei vocabolari da LOV con un thread pool tramite `concurrent.futures`
    - per la renderizzazione uso un template Jinja, un file CSS per lo stile e in aggiunta creo un file JSON di utility contenente i dati
    - Su GitHub faccio un check massivo su tutte le repo pubbliche e in particolare su tutti i file con determinate estensioni di formato
    - Su OpenAlex faccio un check massivo su tutti i work e in particolare su titoli, abstract e testi, ed estraggo in parallelo anche una serie di metadati dei work stessi da utilizzare nel report
- Uso un workflow e GitHub Actions per automatizzare il processo, schedulato al primo di ogni mese alle 08:00
- I file in `docs/` vengono pubblicati tramite GitHub Pages

### Struttura

```
.
├── config.yaml              ← edit this to configure your ontologies
├── main.py                  ← orchestrator (reads config, calls fetchers, writes output)
├── src/
│   ├── fetchers.py          ← API logic (LOV, GitHub, OpenAlex)
│   ├── renderer.py          ← pure HTML generation (no I/O)
│   ├── loader.py            ← loads config and data
│   ├── static/
│   │   └── style.css
│   └── templates/
│       └── report.html.j2   ← report template
├── tests/
│   ├── test_config.py       ← config loading and validation
│   ├── test_fetchers.py     ← mocked fetcher logic
│   └── test_renderer.py     ← HTML output correctness
├── docs/
│   ├── index.html           ← generated report
│   ├── style.css
│   └── data.json            ← JSON snapshot for auditing
└── .github/workflows/
    └── monitor.yml          ← monthly GitHub Actions schedule
```
